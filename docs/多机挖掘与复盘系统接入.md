# 多机挖掘与复盘系统接入

产品目标以 [核心指导思想与产品目标](核心指导思想与产品目标.md) 为准：多台电脑替代逐联赛反复让模型研究，挖掘全部选定历史中的稳定高净胜策略，最后交付精确触发代码。

## 多台机器如何工作

1. 所有机器部署同一个源码版本、受支持的 Python 和锁定依赖。每台电脑使用独立本地工作区。
2. 在一台机器上检查总数据目录并生成计划：

   `python -B app.py fleet-plan D:\足球数据 --nodes 8 --company 皇冠 --output D:\本轮分配`

   生成 `node_001.json` 等节点计划和 `fleet_summary.json`。每个联赛只分配给一个节点，按报价行数尽量平衡；候选数影响后续耗时，因此不承诺各机同时完成。计划写明数据树根目录 `source_data_root`；每个节点计划的 `required_files` 列出该机需要复制的文件（相对该根目录的路径），`required_bytes` 为总大小。
3. 复制同版软件到各机，并按该机计划的 `required_files` 复制数据文件（保持相对路径；分配给其他机器的联赛文件不必复制）。每机导入自己的计划：

   `python -B app.py fleet-import D:\本轮分配\node_001.json --data-root E:\足球数据 --queue`

   `--data-root` 对应计划中 `source_data_root` 的新位置，目录内部相对结构须保持一致。导入核对计划哈希、软件指纹和输入哈希。任务按软件引擎、联赛、公司、该联赛输入哈希与研究配置识别，重复导入或重新生成计划都不会重复建任务。省略 `--queue` 时只登记暂停任务；之后再带 `--queue` 导入会把尚未开始的暂停任务排队，由本机界面服务调度。
4. 双击启动工作台。每机可设置本机同时研究数量；内存和磁盘不足时减少并发，不缩小规则池。各机输出保持各自任务ID和节点来源。
5. 收集每个联赛的最终决定、配置、覆盖账、规则、触发案例和A/B包。先核对版本与输入身份再接入，不能把不同版本结果混在同一名单里。

此实现是离线分配与本地运行；没有自动远程安装、文件传输、远程控制或跨机共享断点。不要在多台机器上共用运行中的 SQLite 文件。数据变化或研究规则变化应生成新计划。

## 速度原则

保留现有 NumPy/Numba 批量评价、全方向共享一次因果扫描、完整掩码缓存、相同历史信号家族的基础指标复用、安全空交集/收益上界证明和持久化断点。

历史模式默认关闭逐规则额外扰动计算，因为它不决定用户的历史目标；可打开用于附加对照，结果不能据此删除第一阶段盈利池。优化前后必须核对盈利表达数、规范规则、首次信号和结算结果；不以压缩搜索范围换取“同范围加速”的说法。

## 复盘系统的当前接入边界

目标路径：`C:\Users\Administrator\Desktop\复盘系统`。本轮只读核对到该项目是 Electron/Node.js 应用，策略模块有 CommonJS/浏览器导出。例如 `lib/crown-live-ah-mined-strategies.js` 暴露：

- `findEntries(input, options)`：寻找触发；
- `selectCurrent(input, enabledStrategies, strategyId)`、`isStillCurrent(input, entry)`：选择与时效校验；
- `evidence(entry)`：触发依据；
- `bet(entry, match)`：候选投注描述。

`lib/crown-candidate.js` 负责候选整合；`lib/crown-bet-safety.js` 还负责机会身份、去重和额度约束。不能只把策略名称加进数组就算完成接入。

当前研究交接包中的精确触发实现是 Python `lab.features.SignalEngine`，并提供 `paper-stream` JSONL 协议。后续需要在复盘系统中新增联赛策略注册层以及经过对照验证的 JSONL 桥接或等价 JavaScript 引擎；此适配层尚未部署，不能直接把 Python 包称作原生 JS 插件。

## 每个联赛必须带走的内容

联赛与公司精确身份、输入与软件指纹、历史区间、完整范围/剩余计数、主名单及较稳定备选、规则内容哈希、精确条件树、报价单位、赛前/滚球阶段、触发优先级、每方向首单与整场上限、历史黄金信号、逐条正负例和恢复测试。

尤其要对齐盘口正负号与四分之一刻度、香港水位、滚球让球的当时比分基准、文字中场、跨市场时效、同分钟末取价和重复消息。已查看的旧策略模块把中场视为45分钟、允许多条方案独立触发；FSL的文字中场和核心方向名额口径不同，迁移时不得直接沿用旧模块的假设。

接入分为：历史包核对 → 新注册层/桥接 → 相同报价逐笔对照 → 新联赛名单启用 → 旧策略停用。用户明确的最终方向是弃用旧策略、使用按联赛挖掘的新策略；旧策略删除、账户连接与真实执行开关属于后续迁移步骤，本轮未操作。
