# 版本、证据与工作区维护

代码版本来自 `lab/common.py`。目录名是路径，不能作为版本证据。`engine_hash`（FSL_ENGINE_INPUTS_V5）覆盖计算源码和运行依赖清单，控制断点、方向缓存及交付的运行内容一致性。它不含前端，也不含不影响研究数字的 NON_SEMANTIC_MODULES：`cli.py`、`fleet.py`、`launcher.py`、`locking.py`、`maintenance.py`、`migration.py`、`packaging.py`、`release.py`、`reporting.py`、`resources.py`、`server.py`、`store.py`。只改这些文件或 CSS/JS/HTML 不会使暂停任务失效；改动特征、搜索、复核、选择、执行、结算、样本外评测等计算模块仍会阻止续跑。`release_hash` 另外覆盖前端、上述模块、配置模板、测试、文档、安装脚本及关键验证维护脚本。SBOM 的应用哈希使用前者并明确标注范围，库组件哈希来自锁文件允许的分发包，不表示对某一台机器的所有已安装文件做了散列。

独立审阅请使用 `validation/frozen_releases/` 中明确版本及指纹的固定副本。当前开发期间的状态、日志会变化；它们不改变旧副本的认证范围。发布前必须停止编辑，检查冻结回归的 `source_unchanged`、`frozen_copy_unchanged` 及两个当前指纹，再固化新目录。SBOM 更新、测试、状态汇总与源码保留有明确先后顺序，见本机 `validation/README.md`。默认单元测试不含端到端流水线，发布前必须另跑 `frozen_regression.py` 的 `--standard-empty` 与 `--standard-nonempty`（验证模式），以及 `historical_acceptance.py` 的 empty、full、limited 三例（默认全历史模式）。没有 Node.js 的机器会跳过两条界面渲染回归，非 Windows 机器会跳过两条文件共享锁回归；这些跳过不计入“2 项按设计跳过”，发布验收应在装有 Node.js 的 Windows 上运行。A/B 研究交接包按其各自 README 验收，不等同于完整开发项目。

日常开发可以走简化路径：改代码 → 单元测试 → 在与活动目录逐文件一致的隔离副本上跑两条合成流水线；只有正式发布才需要冻结副本、finalize/preserve 两个脚本和证据汇总。简化路径的结果不能写成已冻结发布。

Git 已从保存的 0.4.4、0.4.5、0.4.6 源码快照导入版本历史，提交说明明确其导入时间和来源，不伪装成当时的逐次编辑记录。今后的代码和维护工具修改应提交到 Git；不推送外部仓库，不将真实研究数据加入源码仓库。

## 历史任务

旧任务的哈希不会被改成新版本以强行续跑。界面和联赛登记表标明 `resumable` 及阻断原因；仅当前代码一致且处于暂停、错误或中断状态的任务可以续跑。已结束或旧版本任务不能据此恢复。

保留原输入及参数，在新代码下重建为**暂停的新任务**：

    python -B app.py rebuild-job --job 原任务ID

同一原任务/新引擎/参数重复执行会返回同一重建任务。工具核对原输入，原数据或质量清单改变时要求重新导入，不携带旧搜索进度或认证。旧任务配置里已废弃的绝对门槛字段会被列入参数差异后丢弃。需要跨机器找回原数据时，用 import-audit 导入 B 包里的原始输入。

### 2026-09-15 旧任务迁移修订

单条和批量入口都支持 --profile、--config 和 --dry-run。批量入口还支持重复的 --job，只处理列出的ID；省略时检查当前工作区全部任务，不递归迁移嵌套的历史验收工作区。

只读预览旧任务转为当前固定标准（不创建、不排队、不改原任务）：

    python -B app.py rebuild-stale --job 原任务ID --profile standard --dry-run

移除 --dry-run 后，创建暂停的新任务；只有明确追加 --queue 才尝试排队。--dry-run 与 --queue 同时出现时仍只预览，would_queue 表示请求的排队意图，实际排队还须目标为暂停且无进度。已有目标不会被强行重置或再次计算。

默认保留原研究模式和预算；0.6以前未声明目标的任务按 validation 解释。显式 --profile standard 会按目标重置固定标准，不会将 validation 自动变为 historical，也不会清除计算预算。旧 min_matches=80 与当前固定验证标准冲突时，默认拒绝；显式迁移才调整到当前固定值40。配置文件覆盖最后应用，无效的显式参数仍报错，不会悄悄改回合法值。

按全历史模板预览一个旧任务：

    python -B app.py rebuild-stale --job 原任务ID --config config/rebuild_historical.json --dry-run

模板显式选择 historical、standard、compact_v1、16方向、最低净胜10、留出0个月和不限搜索/组合预算，开启交接包，真实下单及第二笔仍关闭。公司、整场上限和内存资源配置沿用旧值；所有实际差异都在 config_changes 中列出。不限预算并不保证数据质量或筛选门禁必定通过。

返回结果分别列出 rebuilt（成功重建）、planned（预览可重建）、failed 和 skipped，并给出每类计数。任何重建或排队失败均返回非零退出码1；成功/无操作返回0，参数解析错误返回2。不要只看进程正常退出或某一条成功。每个新任务保留 rebuild_provenance.json，以及 rebuild_provenance/ 中按来源分开的不可覆盖迁移记录，包含旧/新配置指纹、输入哈希和参数差异。重建不删除旧目录，也不释放旧任务的磁盘占用。

界面按注册表显示旧任务实际状态。暂停/中断任务的 RUNNING 阶段被标作“上次停留于此”，原阶段文件保持原样；仍在运行的任务不会被显示成停止。

## 并行任务

工作台“同时计算的联赛任务数”写入工作区 `scheduler_settings.json`（1—8，默认1）。每个任务占用一个计算槽锁（`.worker.lock`、`.worker_1.lock`……），领取任务时在数据库事务内核对运行数；引擎自检由锁串行化，其他任务等待并复用同一报告。每个并行任务各自占用内存和磁盘，请按机器配置设置。

## 缓存清理

先预览：

    python -B app.py cleanup-workspace

确认预览后执行：

    python -B app.py cleanup-workspace --apply

仅清理无活动任务工作区内、已完成方向的 `masks.sqlite3` 及其已知附属文件、`virtual_columns/`、`review_columns/`。执行时必须同时持有全部计算槽锁，并检查路径边界，跳过链接/外部目录、未完成方向以及缺少重建基础文件的目录。清理期间，工作台调度器启动的计算进程会以代码75退出；若进程以0退出但任务仍在排队，同样保持排队、稍后自动再试，不会被标成错误。原始数据、数组、字典、搜索账本、证明、样本外留出数据、任务状态及交接包均保留。报告的释放量是文件逻辑字节，不是磁盘物理空闲量保证；大目录可能主要是证据，不能按体积直接删除。B 审计包不打包这些可重建缓存，只在 `audit_log_policy.json` 登记路径与大小。

## 缓存报错

| 错误代码 | 含义 |
|---|---|
| SOURCE_CHANGED_DURING_RUN | 本次运行期间计算源码变化，结果拒绝认证 |
| SOURCE_REVISION_MISMATCH | 缓存/任务属于其他计算源码版本，可能是运行中编辑或旧版缓存 |
| CONFIGURATION_MISMATCH | 冻结参数改变 |
| INPUT_DATA_MISMATCH | 输入或预处理清单改变 |
| SCOPE_OR_UNIT_MISMATCH | 方向或水位刻度改变 |
| CACHE_CONTENT_CHANGED / CACHE_FILE_MISSING | 缓存内容校验失败或文件缺失 |
| CACHE_BINDING_MISMATCH | 旧缓存只有聚合摘要，不能可靠细分根因 |

不要把正常的版本漂移保护当作计算算法失败；同时也不要跳过保护继续计算。使用原固定版本完成复核，或明确重建新任务。

`validation/history/retired_scripts/` 保存已退役的 `reconcile_reviews.py` 与 `package_v031.py`：前者会把审查台账改回 0.4.3 口径，后者会把整个 validation 目录打包到项目上级目录。二者默认拒绝运行，仅作历史证据。
